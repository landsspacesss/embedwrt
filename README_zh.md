# EmbedWRT

[English](README.md) | **中文**

一个 ESP32-S3 WiFi 中继路由器。它以 STA 身份接入上游网络，再用自己的 AP 重新广播，
并在两者之间做 NAT。客户端的 DNS 由本机应答，再经 DNS-over-HTTPS 或 DNS-over-TLS
转发，所以查询不会以明文穿过上游链路。全部配置都在网页面板里完成，面板区分管理员与
访客。发布构建可以自行从网络更新，开发构建不会。

单一固件，无操作系统。目标是 16 MB flash + 8 MB PSRAM 的 ESP32-S3
（开发用的是微雪 Waveshare ESP32-S3-DevKit N16R8）。

> **状态：** 可用且日常在用，但这是一个个人项目，不是打磨过的产品。本文只描述
> **已在真机上验证过**的行为，未验证的地方会明确标出。

## 功能

- **带 NAT 的中继** —— 单射频同时做 AP 和 STA，因此不需要切换信道
- **加密 DNS 中继** —— 按 MAC 为每台设备选择 DoH 或 DoT，带缓存与逐解析器的熔断。
  也可以把某台设备固定到明文 DNS，或指定某个解析器，各设备互不影响
- **静态租约** —— MAC 绑定固定地址，基于随项目自带的 IDF DHCP 服务端改造
- **端口转发**、**AP 客户端白名单**、**隐藏 SSID**、发射功率与最大连接数
- **客户端列表** —— 含 AP 侧 RSSI、主机名与在线时长
- **访客模式** —— 未登录的访客只能看到并修改自己那台设备，以及它拥有的 IoT 设备
- **IoT 归属** —— 可把设备标记为 IoT 并指派主人，主人无需登录面板即可管理
- **mDNS** —— 可通过 `http://<主机名>.local/` 访问
- **面板内更新固件**；发布构建还支持**从 GitHub release feed 自动更新**
- **开发者模式** —— 用 API 令牌代替登录来刷写固件，便于脚本化
- **面板中英双语**

## 构建与烧录

需要 ESP-IDF **v6.1.0**。

```sh
. $IDF_PATH/export.sh
idf.py build
idf.py -p /dev/ttyACM0 flash monitor     # monitor 会复位芯片
```

目标芯片已在 `sdkconfig.defaults` 里固定为 `esp32s3`，所以全新检出无需另外执行
`set-target` 就能为正确的芯片构建。

`sdkconfig` 不入版本库。修改 `sdkconfig.defaults` 之后要删掉 `sdkconfig` 再重新构建，
否则重新生成的配置会保留旧值。

## 两个镜像不能混用

每次发布都会带上两份：

| 文件 | 用途 | 怎么用 |
|---|---|---|
| `embedwrt.bin` | **面板更新 / 自动更新** | 设置 → 固件更新，或让设备自己更新 |
| `embedwrt-full-16MB.bin` | **有线烧录 —— 首次安装或救砖** | 从偏移 `0x0` 整片写入，含 bootloader 与分区表 |

`embedwrt-full-16MB.bin` **不能**用于无线更新：OTA 只写一个 app 槽位，而整片镜像包含
bootloader。把它上传到面板会被拒绝（`not a valid firmware image`），但这个错误当然不如
一开始就避开来得省事。

## 通过网络更新

双槽分区表就位之后，`idf.py flash` 只在首次安装时需要。

**改动 `partitions.csv` 需要再插线烧录一次。** 应用的位置会移动，否则引导程序找不到它。
`nvs` 必须保持在 `0x9000`/`0x6000` —— 正是这个偏移让重刷能保住面板密码、静态租约、
DNS 规则、端口转发、ACL 与设备归属记录。NVS 不会被 `idf.py flash` 擦除。

设备保留两个 app 槽位并交替使用。启动回滚已启用：一个**镜像结构合法、但启动阶段就崩溃**
的固件会被引导程序回退，所以刷坏了不至于只能拆机接 USB 才能救回来。

### 自动更新

面板会按设定的频率检查发布源（可选关闭，默认每天），发现新版本后可以**只提示等你确认**，
也可以**直接安装**。默认是提示：重启会踢掉所有客户端，这种事不该在未经你同意时发生。

镜像在切换启动分区之前会先与 release 里的 `embedwrt.bin.sha256` 校验；缺少该校验附件的
release 会被**拒绝**，而不是未经校验就装上去。

### 开发构建与发布构建

有两种构建，区别在于**是否存在更新功能**。

```sh
idf.py build                            # 开发构建：没有更新路径
idf.py -DEMBEDWRT_RELEASE=ON build      # 发布构建：从你自己的仓库更新
```

**开发构建不会自行更新**：没有定时检查，也不会自动安装。但手动检查和手动安装仍然可用 ——
开发更新功能时正是靠这个来测 —— 所以面板会保留整个区块，只把「检查频率」和「自动安装」
两个开关置灰。这是默认行为，所以在改固件时，你的修改绝不会被某个发布版悄悄覆盖。
它的版本号带 `-dev` 后缀，发布脚本会拒绝发布这样的构建。

**发布构建**会检查它**构建来源仓库**的 `releases/latest` 端点，这个仓库由 CI 从
`$GITHUB_REPOSITORY` 注入。因此 fork 出来的项目会从自己的仓库更新，无需任何配置；
设备也永远不会被提供别人仓库构建的固件。

面板手动上传和下面说的开发者令牌，两种构建都可用 —— 它们是明确的主动操作，不是自动行为。

### 开发者模式

用于脚本或 CI 驱动的更新，固件更新接口接受 `X-OTA-Token` 请求头代替管理员会话：

```sh
curl -X POST --data-binary @embedwrt.bin \
  -H "Content-Type: application/octet-stream" \
  -H "X-OTA-Token: <令牌>" \
  http://192.168.4.1/ota
```

默认关闭，在面板里开启时会生成令牌。它**只**授权上述三个路由 —— 令牌泄漏也读不到客户端
列表、改不了 WiFi 设置。它和面板密码一样经明文 HTTP 传输，所以能监听网络的人都能读到。

## 配置

面板地址：连本机 AP 时是 `http://192.168.4.1/`，在上游网络上是它的 DHCP 地址，
或 `http://<主机名>.local/`。

**面板只有 HTTP。** 没有 TLS 服务端，所以输入 `https://` 连不上 —— 而会自动把协议升级到
https 的浏览器同样会失败。

未设置密码之前面板是开放的；**忘记密码后没有任何在线找回手段**。清除密码需要擦除 NVS 分区：

```sh
esptool.py -p /dev/ttyACM0 erase_region 0x9000 0x6000
```

## API

面板是一个静态页面，数据全部来自 JSON 接口，所以界面上能做的事都可以脚本化。

大部分接口需要管理员会话。AP 客户端在**未登录**时可达的是：页面本身、`/login`、
`/logout`、`/api/session`、`/claim`，只读的 `/api/clients`、`/api/leases`、
`/api/dnsrules`、`/api/devices`，以及四个设备级写接口（`/lease/add`、`/lease/del`、
`/dnsrule/set`、`/dnsrule/del`）。这四个刻意不在路由层设为管理员专属：否则它们会先返回
401，逐设备的权限判断根本没机会执行，访客就永远无法修改自己的设备。它们改由归属关系
把关，失败时默认拒绝。

排查问题时常用的有：`/status`、`/api/version`（当前版本与所在槽位）、
`/api/update`（自动更新状态），以及 `/api/dnstest` —— 后者会用**和实际服务客户端
完全相同的那段代码**，对每个已配置的解析器真发一次查询。

## 局限

动手之前值得知道：

- **DoH 保护的是「查询」，不是「连接」。** 紧随其后的 TLS 握手会在明文里带上主机名
  （SNI），所以网络运营方仍然能看到你访问了哪些站点 —— 按名字和地址都能看到。加密藏住的
  是你的 DNS 查询，这不是一个通用的隐私工具。
- **这是 NAT，不是隧道。** 客户端的流量是被转发，不是被封装。上游路由器仍然能看到客户端
  实际去了哪里，只是看到的是**一个** IP 而不是好几个 —— 藏住的是「谁」，不是「做了什么」。
- **没有 TLS 服务端，更新也没有签名。** 镜像的校验值与镜像走同一条连接获取，因此能挡住传输
  截断和损坏，挡不住能同时改写两者的攻击者。请把发布源当作可信来源。
- **一次完整的 TLS 握手在这颗芯片上约需两秒** —— 没有 ECC 硬件加速，纯软件大整数运算。
  会话复用是让它可用的关键，这也是解析器要复用连接的原因。
- **一个射频无法同时关联两个 AP。** 中继固定在上游信道，其 AP 下的客户端在 NAT 后面，
  因此从上游网络无法访问它们。
